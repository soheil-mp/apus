# Data sources and the small-data strategy

> Research notes written on 2026-11-02. Every access pattern below was checked against the live
> service on that date (bucket listings, HTTP headers, sample requests), unless marked otherwise.

Apus combines four sources. One is synthetic and three are public, open-licensed data about the
environment, not about people:

| Source | Role in Apus | Licence | Access | Raw volume at source | What Apus keeps |
| :-- | :-- | :-- | :-- | :-- | :-- |
| Synthetic lidar (Apus simulator) | Primary sensor stream; ground truth for testing | Generated by this project (MIT) | UDP stream or files | ≈ 7.9 MB/s for a 64×1024 sensor at 10 Hz (≈ 680 GB/day) | ≤ 50 MB per site-day after edge reduction |
| Aloft weather-radar bird profiles | Drives bird arrivals in the simulator; reference for cross-checks | CC0 (citation requested) | Public S3 bucket, anonymous | ≈ 1.9 MB per radar-day (CSV) | One radar, a few weeks of migration season (≈ 5–10 MB as Parquet) |
| AHN elevation point clouds (COPC) | Terrain, vegetation and structures for the virtual site; height above ground | AHN1–4 CC0; AHN5–6 CC BY 4.0 | HTTP range requests on public object storage | ≈ 100 MB per 1 km² tile (AHN5) | One window of ≈ 500 m × 500 m at reduced density (≤ 20 MB) |
| Open-Meteo weather | Wind for airspeed correction; rain/fog for clutter; context for activity | Data CC BY 4.0; free API for non-commercial use | HTTPS JSON API, no key | KB per site-day | Hourly variables for the site (KB) |

## 1. Synthetic lidar: the "digital twin" sensor

There is no affordable public archive of ground-based lidar recordings of birds, and recording
real data would need hardware and permits. The project therefore starts from a **physics-based
simulator** (see [ADR-0003](../adr/0003-radar-driven-synthetic-lidar.md)):

- **Scene:** the static background is the real terrain and vegetation of a virtual site,
  taken from AHN.
- **Birds:** arrivals are drawn from real radar profiles (Aloft), so busy migration nights in the
  radar data become busy nights in the simulation.
- **Weather:** real hourly weather (Open-Meteo) drives wind drift, rain clutter and fog.
- **Ground truth:** every simulated bird has a known identity and trajectory, so detection and
  tracking can be measured exactly.

**Volume arithmetic.** A spinning sensor with 64 channels × 1024 columns at 10 Hz produces
655,360 points/s. At ≈ 12 bytes per point (range, reflectivity, signal, ambient) that is ≈
7.9 MB/s, ≈ 28 GB/h, ≈ 680 GB/day. Apus never stores this continuously. The edge keeps
(see [ADR-0004](../adr/0004-edge-first-data-reduction.md)):

- detections and tracks (KB per hour),
- **event snippets**: points in a small box around each confirmed track for a few seconds before
  and after, compressed (KB to low MB per event), and
- one full frame per hour for background quality checks (≈ 0.5 MB compressed).

Target budget: **≤ 50 MB per site-day** (a > 99.99 % reduction), enforced by an automated check.

## 2. Aloft: weather-radar vertical profiles of birds

- **What:** vertical profile time series (VPTS) of bird density, speed and direction per 200 m
  height bin, derived from European weather radars with vol2bird.
- **Where:** public S3 bucket `aloftdata` in `eu-west-1`, readable anonymously at
  `https://aloftdata.s3-eu-west-1.amazonaws.com`. A top-level listing on 2026-11-02 showed the
  prefixes `baltrad/`, `uva/` and `ecog-04003/`, plus `coverage.csv` (≈ 14 MB).
- **Layout** ([Aloft FAQ](https://aloftdata.eu/faq/)):
  - daily: `{source}/daily/{radar}/{yyyy}/{radar}_vpts_{yyyymmdd}.csv`
  - monthly: `{source}/monthly/{radar}/{yyyy}/{radar}_vpts_{yyyymm}.csv.gz`
  - per scan: `{source}/hdf5/{radar}/{yyyy}/{mm}/{dd}/{radar}_vp_{yyyymmddThhmmssZ}_{id}.h5`
- **Sources:** `baltrad` (151 radars, 2012 to present, updated daily), `uva` (24 radars in
  Belgium, Germany and the Netherlands, 2008–2023), `ecog-04003` (84 radars, autumn 2016).
- **Dutch radars in `baltrad/daily/`:** `nldbl`, `nldhl`, `nlhrw`. Apus uses **`nlhrw`
  (Herwijnen, 51.8369° N, 5.1381° E)** as its reference radar.
- **Size and latency (observed):** daily files for `nlhrw` are ≈ 1.8–2.0 MB. The file for a
  given day is written about **three days later** (for example, the 2026-01-01 file was last
  modified on 2026-01-04). The ingestion pipeline must treat data as late-arriving and
  idempotent (see [ROADMAP M9–M10](../../ROADMAP.md)).
- **Schema (header of a live file):** `radar, datetime, height, u, v, w, ff, dd, sd_vvp, gap,
  eta, dens, dbz, dbz_all, n, n_dbz, n_all, n_dbz_all, rcs, sd_vvp_threshold, vcp,
  radar_latitude, radar_longitude, radar_height, radar_wavelength, source_file`. The formal
  definition is the [VPTS CSV table schema](https://aloftdata.eu/vpts-csv/).
- **Licence and citation:** data under CC0. The FAQ asks users of `baltrad` data to cite
  Desmet et al. (2025), acknowledge OPERA, and cite the dataset
  ([doi:10.5281/zenodo.14711024](https://doi.org/10.5281/zenodo.14711024)). Apus records
  this in its attribution registry and in the docs.

## 3. AHN: national elevation point clouds as COPC

- **What:** Actueel Hoogtebestand Nederland, the national airborne lidar survey of the
  Netherlands, classified into ground, vegetation, buildings, water and other classes.
- **Where:** official cloud-optimised point clouds (COPC) on public object storage, base URL
  `https://fsn1.your-objectstorage.com/hwh-ahn`. Path patterns (from the open-source
  [AHN Streamer QGIS plugin](https://github.com/jvdkwast/ahn-streamer), which cites the official
  AHN index):
  - AHN2–AHN5, 1 × 1 km sheets: `{base}/AHN{n}_KM/01_LAZ/AHN{n}_C_{xxxxxx}_{yyyyyy}.COPC.LAZ`
  - AHN6: `{base}/AHN6/01_LAZ/AHN6_{year}_C_{x}_{y}.COPC.LAZ`
  - sheet names are the lower-left corner in RD New (EPSG:28992).
- **Checked:** `AHN5_C_111000_415000.COPC.LAZ` returned HTTP 200, `accept-ranges: bytes` and a
  size of ≈ 100 MB; its header contains the `copc` VLR. The AHN4 sheet at the same location is
  ≈ 132 MB.
- **Why COPC matters here:** a COPC file is a LAZ 1.4 file whose points are organised as an
  octree with an index at the start of the file. A reader can fetch only the octree nodes that
  intersect a bounding box, down to a chosen level of detail, using HTTP range requests. Apus
  reads a ≈ 500 m × 500 m window at reduced density instead of downloading whole tiles, which
  keeps the stored extract to tens of MB at most.
- **Licence:** AHN1–4 are CC0; AHN5–6 are CC BY 4.0 and require attribution (as listed by the
  plugin's metadata). Apus uses AHN5 by default and shows the attribution in the docs and the
  web viewer.

## 4. Open-Meteo: weather

- **Endpoint used for history:** `https://archive-api.open-meteo.com/v1/archive` (reanalysis,
  back to 1940). Checked on 2026-11-02 with hourly temperature, precipitation, wind at 10 m and
  100 m, and cloud cover: a two-day request for one point is ≈ 3 KB of JSON.
- **Gotchas found while testing:**
  - The requested coordinate is snapped to the model grid (51.75° N, 4.85° E came back as
    51.775° N, 4.927° E). Apus stores both the requested and returned coordinates.
  - `visibility` is **not available** from the archive endpoint (its unit came back as
    `undefined`). Fog clutter therefore needs the historical-forecast or forecast endpoints,
    or a fallback rule. This is a data-quality check, not a silent default.
  - Wind speed defaults to km/h. Apus requests SI units explicitly (`wind_speed_unit=ms`).
- **Terms** ([open-meteo.com/en/terms](https://open-meteo.com/en/terms)): the free API is for
  non-commercial use, limited to 600 calls/min, 5,000/hour, 10,000/day and 300,000/month per IP
  and application. Data is CC BY 4.0. Apus makes a handful of calls per day, caches responses,
  and backs off on HTTP 429.

## 5. Sources considered and rejected

| Source | Why it is not used |
| :-- | :-- |
| Citizen-science bird observations (eBird, GBIF occurrences, Waarneming.nl) | Records carry observer identities and locations of people: personal data. Apus processes no personal data. |
| Public lidar recordings of drones (for example MMAUD) | Licence is non-commercial share-alike, recordings are large, and the context is counter-drone work. Not needed while the simulator provides exact ground truth. |
| Camera or acoustic datasets | Out of scope: Apus is lidar-only and avoids imagery and audio for privacy. |
| Vendor sample recordings (spinning and solid-state lidar) | Licences vary and are often unclear. A user's own recordings can be replayed through the real-sensor adapters in M18 without being committed. |
| KNMI open data | Requires an API key and duplicates what Open-Meteo provides for this use. Can be added later behind the same weather interface. |

## 6. Small-data rules

These rules keep storage small while the pipeline stays realistic:

1. **Read windows, not archives.** Range requests for COPC; one radar; one site; selected weeks.
2. **Reduce at the edge.** Raw lidar never leaves the device except as event snippets.
3. **Columnar and compressed.** Parquet with zstd everywhere downstream; LAZ for point snippets.
4. **Budgets as tests.** Each dataset has a byte budget in its data contract; a scheduled check
   fails when a budget is exceeded (see [ROADMAP M12](../../ROADMAP.md)).
5. **Lifecycle rules.** Bronze objects expire after a set number of days in local development;
   only gold tables and a small public sample are kept long term.
6. **No data in Git.** Data directories are ignored. Tests use tiny synthetic fixtures generated
   from seeded scenarios.

| Store | Budget (local development) |
| :-- | --: |
| Lakehouse total (object storage) | ≤ 2 GB |
| Lakehouse catalog (PostgreSQL) | ≤ 200 MB |
| AHN extract per site | ≤ 20 MB |
| Aloft extract | ≤ 50 MB |
| Edge buffer on device | ≤ 1 GB ring buffer |
| Git repository | ≤ 50 MB |
| Published web demo sample | ≤ 25 MB |
